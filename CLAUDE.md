# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

YATA ("Yet Another Task App", pronounced **"YAH-tuh"** — *ya* as in *yard*, *ta* as in *factory*) — a Material 3 Expressive task manager for Android, built with Jetpack Compose, Room, and Hilt. Gradle root project name is `TodoExpressive` (legacy); package/app id is `com.mj.yata`. Two modules:
- `:app` — the phone app (`com.mj.yata`, minSdk 26, compileSdk/targetSdk 35).
- `:baselineprofile` — a `com.android.test` module that records the ART baseline profile packaged with the app.

## Commands

All commands run from the repo root using the Gradle wrapper (`./gradlew` on Bash, `gradlew.bat` on native Windows shells).

```bash
# Default verification for small Kotlin/UI changes: fast correctness check, no packaging.
./gradlew :app:compileDebugKotlin -q

# Full debug build
./gradlew :app:assembleDebug -q

# Install to a connected/emulated device
./gradlew :app:installDebug -q

# Unit tests (JVM, no device). Run only when the touched logic needs test coverage or the user asks;
# even a focused --tests run still walks a much heavier Android unit-test graph than compileDebugKotlin.
./gradlew :app:testDebugUnitTest
./gradlew :app:testDebugUnitTest --tests "com.mj.yata.RecurrenceEvaluatorTest"
./gradlew :app:testDebugUnitTest --tests "com.mj.yata.RecurrenceEvaluatorTest.testWeeklyRecurrence"

# Instrumented tests. DESTRUCTIVE — see the warning below; -PdisposableDevice is required, and the
# build refuses to run without it. Note `--tests` does NOT work here; that is Gradle's unit-test
# filter, and connectedAndroidTest takes a runner argument instead.
./gradlew :app:connectedDebugAndroidTest -PdisposableDevice   # whole suite
./gradlew :app:connectedDebugAndroidTest -PdisposableDevice -Pandroid.testInstrumentationRunnerArguments.class=com.mj.yata.data.local.db.AppDatabaseMigrationTest

# Compose UI smoke suite (launch, add, complete, tab switch, delete-undo)
./gradlew :app:connectedDebugAndroidTest -PdisposableDevice -Pandroid.testInstrumentationRunnerArguments.class=com.mj.yata.MainScreenSmokeTest

# Regenerate the baseline profile (needs a rooted/userdebug device or emulator, API 28+)
./gradlew :baselineprofile:generateBaselineProfile
```

After changing anything under `app/src/main/java`, the fast loop is `compileDebugKotlin` to catch errors, then `installDebug` before manually verifying in the UI. `MainScreenSmokeTest` covers only the core add/complete/delete paths, so anything beyond those still needs a manual pass on-device.

**Never run instrumented tests against the user's phone.** `connectedAndroidTest` is not read-only: it reinstalls the app, and the tests add, complete and delete real rows in whatever database is on the device. It also used to uninstall the app on completion, wiping the Room database and DataStore — which is exactly how a real day's data was destroyed on this project. Two guards now exist: `android.injected.androidTest.leaveApksInstalledAfterRun=true` in `gradle.properties` stops the uninstall, and a `doFirst` check in `app/build.gradle.kts` refuses the task without `-PdisposableDevice`. **Do not pass that flag on the user's device**, and don't work around either guard — they exist because the failure is silent until the data is gone. Emulator or a spare device only, and ask first.

More generally: confirm before any command that can remove the app or its data — `adb uninstall`, `pm clear`, `installDebug` over a different signing key, or anything that resets storage. The user's phone is their daily driver, not a test rig.

**Never drive the device to take screenshots.** Do not use `adb shell screencap`, `uiautomator dump`, `adb shell input tap/swipe/keyevent`, or any other means of navigating the running app to look at it. Build, install, and describe what changed — visual verification is the user's, and they will send a screenshot when they want one. This applies even when a UI change would obviously benefit from being seen.

## Changelog

`CHANGELOG.md` is maintained by hand, newest first, in Keep a Changelog format. **Any change a user
would notice goes under `[Unreleased]` in the same commit that makes it** — not batched up at
release time. Internal refactors, build plumbing and test-only work stay in the commit message
unless they change behaviour.

Releasing: rename `[Unreleased]` to the new version with a date and `versionCode`, open a fresh
empty `[Unreleased]` above it, add the compare/tag links at the bottom, then use that section
verbatim as the GitHub release notes (`gh release create <tag> <apk> --notes-file …`). The release
notes and the changelog should never be written twice.

## Architecture

**Layering:** `domain/model` (plain data classes, no Android/Room deps) → `data/local/db` (Room entities/DAOs) → `data/mapper` (Entity ⇄ domain model conversion) → `data/repository/YataRepositoryImpl` (implements `domain/repository/YataRepository`, exposes `Flow`s) → `ui/screen/main/MainViewModel` (single large ViewModel backing the whole app, exposes `StateFlow`s and imperative methods like `deleteTask`, `bulkDeleteTasks`, `toggleTaskDone`) → Compose screens under `ui/screen/*`. Screens read from `MainViewModel` (obtained via `hiltViewModel()`) rather than each having their own ViewModel — there is one ViewModel per app, not per screen. Heavier multi-step logic is injected into it as `domain/usecase/TaskOperations` and `domain/usecase/BackupOperations` rather than living inline.

**Database (Room, `data/local/db/AppDatabase.kt`):** currently at version 33 (24 added `tasks.seriesId` + index, linking a recurring task to its historical completed instances for the reliable streak in `RecurrenceEvaluator.computeStreak`; 25 added `tasks.archived`; 26 added `tasks.startDate`; 27 added `tasks.createdAt`, deliberately left null on existing rows rather than backfilled so age/turnaround metrics on Analytics don't misdate a pre-existing backlog to the upgrade date; 28 added `tasks.followUpAt`; 29 added `projects.sectionNames`; 30 added `tasks.estimateMinutes`; 31 added `tasks.ownerId`, backfilled from each task's first `task_person_cross_ref` row by insertion order so single-owner assignment survives the move off the old many-to-many table; 32 added `tags.description`; 33 added `tasks.postponementCount`). Every schema change is a hand-written `Migration` object added to the `companion object` and registered in `di/DatabaseModule.kt`'s `.addMigrations(...)` call — there's no auto-migration. `fallbackToDestructiveMigrationOnDowngrade()` only fires on a genuine version *downgrade* (e.g. reinstalling an older APK); a missing forward migration throws instead of silently wiping data. When adding a column/table: bump the version in `@Database`, add a `MIGRATION_N_N1` object, register it in `DatabaseModule`, and add a migration test to `AppDatabaseMigrationTest`. Row-scoped booleans/soft-deletes follow existing conventions — e.g. `tasks.deletedAt` (non-null = in Trash, not hard-deleted) and `projects/lists.excludeFromToday`.

Entities beyond the obvious five: `TaskFtsEntity` (FTS mirror of tasks), `TaskPersonCrossRef`/`TaskTagCrossRef`, `SubtaskEntity`, `TaskCommentEntity`, and the grouping tables `TagGroupEntity`/`PersonGroupEntity`.

**Tag/person groups:** a tag references its group by `tags.groupId`; the group row must exist first. Creating a group and assigning tags to it is one transactional repository call — `YataRepository.upsertTags(tags, pendingGroup)` and `setTagsGroup(tagIds, groupId, pendingGroup)` — never two separate async writes. Bulk assignment goes through a direct DAO `UPDATE tags SET groupId = …` so it can't re-upsert a placeholder group or clobber an existing group's name. A typed new-group name in the tag editor is applied by the main Save/Create button (an inline confirm affordance must not be required), and a name matching an existing group reuses that group. This shape exists because the earlier non-transactional flow silently dropped assignments — `tag_groups` came back empty on-device; see `HANDOFF.md` §3.

**Navigation:** single-Activity, `ui/navigation/AppNavigation.kt` defines routes (`Screen.kt`) over a `NavHost`. `Screen.Main` is a 5-tab shell (`MainScreen.kt` → `CustomBottomNav` with ids 0=Today, 1=Projects, 2=People, 3=Tags, 4=Upcoming, fixed regardless of which tabs are hidden by feature flags) with its own drawer, FAB, and — as of the delete-undo work — a shared `SnackbarHostState` at the `MainScreen` Scaffold level for cross-tab bulk actions. Detail screens (task/project/list/tag/person, search, settings, trash, archive, analytics, help/about, next-days, welcome) are separate top-level destinations, each usually with its own `Scaffold`/`SnackbarHostState` when they need one (see `SearchScreen.kt`). `Screen.HelpAbout` and `Screen.Settings` were split apart (help/about used to be a card inside Settings); `Screen.NextDays` is a standalone 10-day lookahead reachable from Today's top bar and the command palette. The old collapsible drawer "Tools" section is gone: the drawer has one Command palette entry, and the former tool rows (My Work, Focus Mode, Morning/Evening Review, Stale Nudges, Task Health) are searchable palette presets. Add new drawer-only surfaces sparingly; prefer the palette for saved searches and command-like destinations.

Current non-Main destinations (`Screen.kt`): TaskDetail, ProjectDetail, PersonDetail, `PersonAnalytics`, `StaffAnalytics`, TagDetail, ListDetail, Welcome, Search, Settings, `SettingsSection` (one route per `SettingsDestination`), HelpAbout, Analytics, Trash, Archive, NextDays, `CrashLog`, `ShareApp`, `RemoteSync`, `SharedTaskImport`. Remote-sync configuration is its own screen, not a Settings dialog.

**Adaptive layout (`ui/util/AdaptiveLayout.kt`):** tablets/foldables are handled by width thresholds off `LocalConfiguration.screenWidthDp`, not `WindowSizeClass`. `rememberAdaptiveLayoutInfo()` returns `isWide` (≥600dp) plus a `contentMaxWidth` (760/920/1040dp at 600/840/1200dp, `Dp.Unspecified` on phones); `AdaptiveContentBox` centers content within it, and `rememberAdaptiveSheetMaxWidth()` caps bottom sheets at 640dp when wide. `MainScreen` swaps `CustomBottomNav` for a `MainNavigationRail` when `isWide`, and suppresses the drawer menu button in that mode. New full-screen surfaces should wrap their content in `AdaptiveContentBox` and new `ModalBottomSheet`s should pass `sheetMaxWidth = rememberAdaptiveSheetMaxWidth()` — otherwise they stretch edge-to-edge on a tablet.

**Voice capture (`data/voice/OnDeviceVoiceRecognizer.kt`):** wraps Android `SpeechRecognizer`, preferring on-device recognition, and exposes a `VoiceState` (`Idle/Listening/Speaking(partialText, rmsDb)/FinalResult/Error`) `StateFlow` driving `ui/widgets/VoiceTaskOverlay.kt`. Used from `NewTaskSheet` and `QuickAddDialogActivity`; the transcript feeds `NaturalLanguageParser` like typed text. Voice language is user-selectable from Settings (`voiceRecognitionLanguageFlow`, default `"default"`), and strict offline mode is retried per language: if the platform reports an offline language as unavailable, that language is remembered and future starts fall back instead of repeatedly failing.

**Natural language recognition (`util/NaturalLanguageParser.kt`, `util/nl/`):** the parser has been split into typed rule groups (`DateRules`, `StartDateRules`, `TimeRules`, `ReminderRules`, `RecurrenceRules`, `PriorityFlagRules`, `EntityRules`) plus support objects (`ParserContext`, `ParseState`, `EscapeRules`, `NaturalLanguageTitleCleaner`, `NaturalLanguageCounts`). Keep new behavior inside the matching rule group and cover it in `NaturalLanguageParserTest`; avoid adding screen-local parsing shortcuts. `ClaimTracker` in `NaturalLanguageClaims.kt` owns overlap prevention and typed highlight claims, so anything recognized should claim its consumed range with the right type instead of stripping text ad hoc.

**NL languages and normalization:** Latin-script multilingual aliases live in `NaturalLanguageLexicon.kt` as `LanguagePack` data (`weekdayNames`, `monthNames`, `relativeDateWords`, etc.). Add/edit language words there and cover them in `NaturalLanguageLexiconTest`; broad native-script support is intentionally out of scope unless the normalization/range mapping is extended for it. `NaturalLanguageInputNormalizer` maps voice-friendly text and punctuation variants to normalized text while preserving raw-input ranges; parser highlight spans must map back through `NormalizedInput.rawRangeForNormalizedRange` before display so dictated text highlights the user's original words.

**NL highlighting:** `ui/widgets/QuickAddHighlightTransformation.kt` is the shared visual transformation for recognized keywords. It is used by the new-task sheet, widget quick add, and the edit-task title field in `TaskDetailScreen`; do not fork the highlight logic per screen. Highlight colors are keyed by claim type (due/start date, time/reminder, recurrence, priority/flag, project/list/tag/person), so when adding a new detected field, add a typed claim and extend the shared style mapping if needed.

**Known NL follow-up:** a deeper recurrence alias/table migration was explored and backed out because it changed parser behavior under tests. The committed state is stable; treat recurrence alias restructuring as a separate behavior-preserving pass with tests rather than continuing it casually.

**Crash log:** `YataApplication` installs an uncaught-exception handler that writes to `data/local/crash/CrashLogStore` before the process dies (the recording itself is wrapped so crash logging can never throw during a crash); entries are viewable at `Screen.CrashLog` from Settings.

**App lock (`data/local/datastore/UserPreferences.kt`, `util/PinCodeUtils.kt`):** an optional PIN/biometric gate (`appLockEnabledFlow`, timeout in `appLockTimeoutMinutesFlow`) checked at `MainActivity` launch and resume. The PIN itself is never stored in plain text — `hashPin`/`verifyPin` use salted PBKDF2WithHmacSHA256 (120k iterations, prefix `pbkdf2s256:`); a PIN set under either older scheme (`pbkdf2:` = PBKDF2WithHmacSHA1, or no prefix = a single-round SHA-256 predating PBKDF2 entirely) still verifies once and is transparently upgraded on the next successful unlock, see `needsRehash`. Comparison goes through `MessageDigest.isEqual` rather than `==` to avoid a timing side-channel. While app lock is on, `MainActivity` also sets `WindowManager.LayoutParams.FLAG_SECURE` on the window — otherwise the lock screen would guard nothing, since the same task content it hides sits in the Overview/recents thumbnail and is screenshot-able regardless. `datastore/` (which holds the PIN's hash and salt) is excluded from Android's device backup — see the sync baseline note below for why.

**Feature flags:** People/Tags/Projects are optional and can be hidden entirely via `UserPreferences` (`peopleFeatureEnabledFlow`, `tagsFeatureEnabledFlow`, `projectsFeatureEnabledFlow`, backed by DataStore in `data/local/datastore/UserPreferences.kt`). Any new screen/tab/bulk-action surface touching these entities should gate on the corresponding `*FeatureEnabled` `StateFlow` from `MainViewModel`, matching existing tabs.

**Task list screens share structural patterns**, not a shared composable hierarchy — each of Today/Project/List/Tag/Person independently splits its tasks into "Pending"/"Completed" sections (header via `ui/widgets/TaskSectionHeader.kt`, hidden when empty or when completed tasks are toggled off) and independently wires an eye-icon `hideCompleted` toggle. `ui/widgets/DragDropReorderableColumn.kt` is the shared long-press drag-to-reorder `LazyColumn` used by screens with manual ordering (Project/List detail); it supports non-draggable `header`/`footer` `LazyListScope` slots (e.g. the Pending/Completed headers and the static Completed list) via a `headerItemCount` offset that keeps its internal drag index math in the same "global" index space as `LazyListState.layoutInfo`.

**Delete-with-undo pattern:** deleting a task (single, from `TaskDetailScreen`, or bulk, from Today/Upcoming/Search's multiselect toolbar) does not delete immediately — it shows a `Snackbar` with an Undo action and only calls the repository delete if the window elapses untouched. Go through `showUndoSnackbar(hostState, message, seconds)` in `ui/widgets/UndoSnackbar.kt` rather than calling `showSnackbar` directly: it returns `true` when Undo was tapped (so the caller must *not* perform the action). `SnackbarDuration` only offers Short/Long and neither is configurable, so the helper shows the snackbar as `Indefinite` and times it out with `withTimeoutOrNull`. The window is user-configurable (Settings → Sound & Feedback: 4/8/15s, default 4) and reaches composables as `LocalUndoWindowSeconds` (provided in `MainActivity` from `undoWindowSecondsFlow`); `DeleteUndoSnackbar.kt`'s countdown reads that same CompositionLocal so the visible number and the real deadline can't drift apart. The host picks the custom rendering by checking `data.visuals.actionLabel == UNDO_ACTION_LABEL` — that constant stays untranslated on purpose (it's never displayed, and localizing it would break the equality check in every non-English locale).

**Search (`ui/screen/search/SearchScreen.kt`):** the DAO query covers only live tasks, so the "Archived" / "Trash" filter chips are satisfied client-side — they union `viewModel.archivedTasks` / `deletedTasks` into the result set and filter them with the local `Task.matchesSearchText` helper (title, notes, assignee names, effective tags, subtask titles), since the SQL `LIKE` search excludes both. Anything that changes the search haystack has to change in both places to stay consistent.

**Task postponement tracking (`domain/model/TaskPostponement.kt`, DB 33):** `tasks.postponementCount` increments whenever a task's due date is edited forward (`isPostponedLater`/`nextPostponementCount` compare old vs. new ISO due strings). Surfaced on `TaskDetailScreen` and rolled up on `AnalyticsScreen`. `postponementWarningThresholdFor(priority, normalThreshold)` derives a lower per-priority warning threshold from the user-configured base (Settings → Task Defaults, 1-10, default 3) — high-priority tasks warn much sooner (can hit 0, i.e. warn immediately) than medium/normal, since a repeatedly-postponed urgent task is a bigger problem than a low-priority one.

**Weekend reschedule warning (`domain/model/WeekendReschedule.kt`):** a second, independent warning living alongside postponement tracking, sharing its plumbing shape but not its trigger condition. `weekendDaysFlow` (`UserPreferences`, `stringSetPreferencesKey`, RFC5545 two-letter day codes — the same vocabulary `Recurrence.byday` uses, default `{"SA","SU"}`) is configured via a 7-day chip row in Settings → Task Defaults; an empty set turns the feature off rather than needing a separate enabled flag. `isRescheduledToWeekend(previousDue, nextDue, weekendDays)` fires whenever the due date actually changes (not on an unrelated edit of a task already due on a weekend) *and* lands on a configured day — in either direction, unlike postponement, which only counts a move later. `MainViewModel.warnIfRescheduledToWeekend` is called from the same three choke points as `warnIfPostponedOften` (`upsertTask`, `quickSnoozeTask`, `bulkRescheduleTasks`); `TaskOperations.quickSnooze`/`bulkReschedule` had to stop pre-filtering their return value down to only postponement-worthy changes so both warnings can independently decide whether to fire off the same full result. Deliberately scoped to just this warning and the Settings picker — the four existing places that already hardcode Saturday/Sunday as "the weekend" (`TaskOperations.nextWeekday`, the NL parser's "this weekend" phrases, the "weekends" recurrence alias, `RecurrenceEvaluator`'s summary label) are untouched, since redefining what those mean is a separate, bigger pass.

**Task duplication:** `TaskOperations.duplicateTask`/`bulkDuplicate` append " Duplicate" to the copy's title (`duplicateTaskTitle`, `TaskOperations.kt`) rather than leaving it identical to the source, and both now return the created `Task`(s) to the caller instead of `Unit` so call sites (e.g. jumping to the new copy) don't have to re-query.

**Task share/import links (`util/export/TaskTransferLink.kt`):** exporting a task/project/list/tag/person as image or PDF can embed one HTTPS App Link (`https://ranjithj.in/yata/i#...`) in the share text; the payload lives in the URL fragment so it never reaches the web server or link-preview crawlers. `MainActivity` intercepts these before ordinary deep-link routing; a single-task link opens prefilled in `NewTaskSheet` (via `resolveAgainstLocalData`) for the receiver to edit before saving, while a multi-task link goes through a preview/confirm screen (`ui/screen/sharedimport/SharedTaskImportScreen.kt`) and only writes after explicit Import. Shared tasks carry title/priority/flag/notes/subtasks/dates/time/estimate/recurrence/list-project-tags (structure optionally recreated by name) but deliberately drop sender-local fields — reminder, section, done state, follow-up, archive/trash state — and never copy or assign people (local identity records, left behind on purpose). Legacy `yata://` link forms remain decode-only for compatibility. Alongside the existing `MAX_DECODED_BYTES` (payload) and `MAX_TASKS_PER_LINK`/`MAX_SUBTASKS_PER_TASK` (row counts) caps, `parseTransferLink` also rejects a link with any single oversized text field (`MAX_TEXT_FIELD_LENGTH`/`MAX_NOTES_FIELD_LENGTH`) — the other caps bound the payload and the row counts, but not one pathologically long title/notes/name within an otherwise-small link. Full format/hardening details and file map: `docs/app-links-handoff.md`. A diagnostic card under Settings → Diagnostics (`ui/screen/crashlog/CrashLogScreen.kt`, moved there from Help & About) reads Android 12+ domain verification state for `ranjithj.in` and opens system link settings.

**Start dates (deferral):** `Task.startDate` ("YYYY-MM-DD", nullable, DB 26) is the "not actionable before" mirror of `due`'s "not after". A task whose start date is in the future is *deferred*: filtered out of Today, but otherwise untouched — still in its project/list, still searchable, badged "Starts <date>" by `TaskRow`. Distinct from both Trash and Archive, and it needs no background job: the filter is evaluated against the current date on read, so a task un-defers itself when the day arrives. Test the predicate through `Task.isDeferredOn(today)` rather than comparing `startDate` inline — it compares ISO strings (lexicographic order matches chronological), treats completed tasks as never-deferred, and fails toward *visible* on a malformed value, since a task wrongly shown is a nuisance while one wrongly hidden is lost.

**Task capture (`ui/sheets/NewTaskSheet.kt`):** the sheet hands its collected fields to callers as a single `NewTaskDraft`, not as a positional parameter list — add new task fields to that data class, not to the lambda signature. It used to be 14 positional parameters destructured identically at 6 call sites, on the one method whose register allocation has already overflowed once (see the toolchain note below); each added parameter pushed it back toward the limit, and every call site had to change. `MainViewModel.addTask(draft)` is the single place a draft maps onto the domain model.

 `NaturalLanguageParser` output is surfaced as a "smart add understood this task as" preview card — a chip per detected field (due, time, repeat, reminder, priority, flag, project, list, tags, people), dismissible, with a manual pick always overriding the parse (the `*ManuallySet` flags). The Repeat panel's custom option opens `RecurrenceSheet` in a nested `ModalBottomSheet`. `QuickAddDialogActivity` (the widget entry point) mirrors the same preview but stands alone — it goes to the repository directly, not through `MainViewModel`.

**Error handling on write paths:** `MainViewModel` never calls `viewModelScope.launch` directly — every write goes through its private `safeLaunch`, which catches `Throwable` (rethrowing `CancellationException`), logs, and emits a `@StringRes` id to `ui/error/AppErrorBus`. Room throws for reasons that aren't bugs and can't be prevented at the call site (FK violation from a concurrently deleted row, full disk, `SQLiteDiskIOException`), and in a bare `launch` any of those reaches the thread's uncaught handler and kills the app mid-action. New ViewModel methods must use `safeLaunch`; note the lambda label is `return@safeLaunch`, not `return@launch`. `AppErrorBus` is a `@Singleton` rather than ViewModel state because `MainViewModel` is scoped to the Main nav entry while the failure can happen several destinations deep — `MainActivity` collects it into a `SnackbarHost` layered over the whole `NavHost`, so one collector covers every screen. `UserPreferences` applies the same principle to reads: all `dataStore.data` access goes through a private `prefsFlow` that catches `IOException` and emits `emptyPreferences()`, so a corrupt prefs file degrades to first-launch defaults instead of crashing every collector. Writes are deliberately left unwrapped so a failing write still surfaces to its caller.

**Home-screen widgets (Glance, `widget/`):** each widget (`YataAppWidget`, `SingleListWidget`, `QuickAddWidget`, `ProgressStatsWidget`, `UpcomingWidget`, `TeamOverdueWidget`) is instantiated directly by Android (`new SomeWidget()`), not through Hilt, so it can't get constructor injection — instead it reaches app dependencies via `WidgetEntryPoint`, a `@EntryPoint` Hilt interface exposing `repository()`/`userPreferences()`. `WidgetUpdater.notifyTasksChanged()` is the single hook called after any task write; it refreshes all placed widget instances via `WidgetRefresher` and debounces the cloud-backup upload. All six widgets share one configure Activity, `WidgetCustomizerConfigActivity` (`Theme.Yata.Transparent`), for corner radius / custom label / M3-colors toggle / opacity / accent-color override; Single List and Quick Add additionally get a source picker (list/project/tag) from the same screen. Each widget's `provideGlance` must explicitly read+apply every `WIDGET_*_KEY` it wants to support — the config screen doesn't know which keys a given widget type actually renders, so a widget that's supposed to honor a shared option but doesn't read it fails silently (this bit `TeamOverdueWidget` once; see `supportsM3Colors` in `WidgetCustomizerConfigActivity` for how an unsupported option gets hidden instead of silently ignored).

**Reminders/notifications (`notification/`):** `ReminderScheduler`/`TaskReminderScheduler` schedule via `AlarmManager`, delivered by `ReminderReceiver`; `BootReceiver` reschedules everything on device reboot; `NotificationActionReceiver` handles notification-inline actions (e.g. mark done) without opening the app. `DailyAgendaWorker` and `OverdueEscalationWorker` are WorkManager jobs (not `AlarmManager`) for, respectively, a daily agenda summary notification and escalating overdue-task nudges. Both are user-controllable (Settings → Notifications: a toggle each, plus a time picker for the agenda, default 07:30) and `YataApplication` reconciles them against preferences on every start; toggling reschedules/cancels immediately. `DailyAgendaWorker.schedule(hour, minute)` enqueues with `ExistingPeriodicWorkPolicy.UPDATE` — with `KEEP` the already-enqueued job wins and a time change silently never takes effect.

**Remote sync and backup (`data/sync/`, `data/sftp/`, `data/ftp/`, `data/github/`):** remote backups use the same JSON format as `JsonExporter`, optionally encrypted with the configured passphrase, and sync through a `SyncTransport` abstraction. FTPS (`data/ftp/FtpBackupManager.kt`) installs the platform CA trust manager on `FTPSClient` unconditionally, but only calls `setEndpointCheckingEnabled(true)` (checking the certificate's name actually matches the configured host, not just that some CA signed it) when the user has opted into Settings → Remote sync → FTP → "Strict certificate verification" (`ftpStrictTlsFlow`, default off) — many self-hosted FTPS servers carry a certificate with no matching SAN, so defaulting this on would silently break an already-working backup instead of surfacing a one-time choice. SFTP (`data/sftp/SftpBackupManager.kt`) needs the bundled Bouncy Castle provider for algorithms Android's stock providers don't cover (Ed25519, curve25519-sha256); `BouncyCastleSupport.ensureRegistered()` does that lazily from `buildClient()` — the single choke point every sshj call routes through — rather than from `Application.onCreate`, and **appends** the provider instead of `insertProviderAt(_, 1)`. Both matter: constructing the provider registers ~1000 algorithm mappings on the main thread (a cold-start cost for the majority who never configure SFTP), and taking slot 1 puts Bouncy Castle's pure-Java `AESEngine`/`GCMBlockCipher` ahead of the platform's hardware-accelerated AES-GCM for `BackupCrypto`, `EncryptedFile`, `EncryptedSharedPreferences` and `GitHubConfigTransfer`. sshj resolves crypto by provider *name*, so it needs Bouncy Castle registered, not first — new sshj entry points must stay downstream of `buildClient()` or call `ensureRegistered()` themselves. SFTP/FTPS/FTP are lock-based transports with rotated history files; GitHub (`GitHubSyncManager`/`GitHubSnapshotPublisher`/`GitHubApi`, ~900 lines) instead uses git commit history and fast-forward-only ref updates on a `yata/snapshot.json` path in the configured repo — no clearable lock, since a commit either lands or doesn't. Every read verifies the returned blob's SHA1 against its content (`GitBlobSha`) before trusting it, and every write re-reads the branch head afterward to confirm GitHub actually kept the uploaded commit (`verifyPublishedHead`) rather than assuming a 200 meant success. Publish is compare-and-swap over the branch ref (`createRef`/`updateRef`, retried up to `MAX_CAS_ATTEMPTS = 3` on a concurrent-update conflict) — not a merge; the merge itself happens locally beforehand via `SnapshotSyncEngine.prepare`, so what's pushed is already the merged result. `SnapshotMerger.normalizeForSync` drops device-local settings (`remote_backup_protocol`, `app_lock_*`, `github_*`, `sftp_*`, `cloud_backup_*`, `local_backup_*`, etc.) and malformed portable setting rows before comparing snapshots; settings rows are keyed by `name`, while every other synced collection is keyed by `id`, so record merge code must preserve the correct identity field. Before every sync, `ensureHeadHasNotRewound` walks the stored `lastObservedHead` against current history (BFS ancestor check, capped `MAX_ANCESTRY_COMMITS`) and refuses to proceed with a `GitHubHistoryRewrittenException` if the branch was force-pushed since — this is a "stop and ask the user to reconnect" case, not something to silently paper over. If the user intentionally trusts GitHub over the local device, Remote sync > GitHub > Recovery exposes "Use latest GitHub snapshot", which calls `BackupOperations.restoreLatestRemoteSnapshot()` to import the newest restore point after saving a recovery backup; `GitHubSyncManager.restore()` also writes that commit id back to `github_last_head_sha`, so the force-download path advances the ancestry checkpoint instead of immediately failing the next sync. If the head snapshot fails validation, `findRecoverySnapshot` walks back through `MAX_RECOVERY_COMMITS` prior commits for the newest one that still validates. A first sync against a repo that already has a snapshot (`allowInitialJoinMerge`) shows a merge summary and needs explicit confirmation before it touches local data. A second, distinct guard covers the *restored-device* shape rather than the first-sync shape: `localLooksUnexpectedlyEmpty`/`SnapshotSyncEngine.checkLocalNotUnexpectedlyEmpty` throws `EmptyLocalDataConfirmationRequiredException` when this device already has a sync baseline with data and the remote still has data, but local now has none — Android's auto-backup can restore the small `yata-sync/` baseline and `datastore/` preferences without the (excluded, much larger) Room database, and a three-way merge in that state resolves as a legitimate, non-conflicting deletion, silently dropping every remote record with no recovery backup taken since nothing appears to change locally. `res/xml/backup_rules.xml` and `data_extraction_rules.xml` exclude both `yata-sync/` and `datastore/` for exactly this reason (the latter also keeps the app-lock PIN's PBKDF2 hash off Android device backup) — a restored device is meant to look like a first join, not this in-between state. `SnapshotMerger.removedAnyRecords` is a second, independent trigger for `SnapshotSyncEngine.commit`'s pre-apply recovery backup: it fires whenever a merge dropped a record the device had at the start of `prepare`, even if the device's current export already happens to match the merge result (so there is nothing to *write* locally) — that combination is exactly the shape of unnoticed data loss the recovery backup exists to catch. `allowEmptyLocalOverwrite` is this guard's escape hatch, threaded through `SyncRunOptions` the same way `allowInitialJoinMerge` is, wired to a "Restore from remote" (safe, via `restoreLatestRemoteSnapshot`) vs. "Sync anyway" (explicit, destructive) dialog in both `MainScreen` and `SettingsScreen`. `HttpGitHubApi` has separate helpers for path segments, slash-preserving paths, and query values (`pathSegment`, `pathWithSlashes`, `queryValue`); use them instead of hand-built URL escaping, especially for branch names with `/` or spaces. `BackupOperations.runRemoteSync` leaves a terminal failure message in the Today sync pill for 8 seconds, including the first useful exception reason, so keep thrown sync errors actionable and user-safe. `UnifiedBackupWorker.backupFailureShouldRetry` treats `GitHubAuthException`/`GitHubPermissionException`/`GitHubNotFoundException`/`GitHubHistoryRewrittenException` as permanent (record and stop retrying — the next attempt would fail the same way) and everything else (network blips, `GitHubConflictException`) as transient. `UnifiedBackupWorker` is the WorkManager job for scheduled/background backups. Independent of the local `Trash`/undo path — this is off-device redundancy, not soft-delete.

**Archiving:** Projects, Lists, People, and (since DB 25) individual **Tasks** each support archive (distinct from Trash's soft-delete) — a hide-without-deleting state with dedicated DAO-backed archive streams, surfaced via each entity's detail/list screens. Don't conflate with `deletedAt`/Trash; archived rows stay fully intact and excluded only from default listing queries (`searchTasksWithRelations` filters `archived = 0` as well as `deletedAt IS NULL`). Archived tasks get their own destination, `Screen.Archive` → `ui/screen/archive/ArchiveScreen.kt`, which splits them into shelved-active vs shelved-completed sections and unarchives with an undo snackbar. **Auto-archive** (Settings → Backup & Data: Off / 7 / 30 / 90 days, off by default) runs from `MainViewModel.init` alongside `purgeOldTrash`; the query deliberately skips rows with a null `completedAt` (tasks completed before that column existed — treating null as "very old" would swallow the whole completed history on first run) and only notifies widgets when it actually moved something.

**Tasker integration (`tasker/createtask/`):** exposes a "Create Task" Tasker plugin action (`com.joaomgcd:taskerpluginlibrary`) — `CreateTaskConfigActivity` is the Tasker-facing config UI, `CreateTaskRunner` executes the action against the repository directly (not through `MainViewModel`, since it runs outside the app's Activity). The library's `com.joaomgcd.taskerpluginlibrary.action.BroadcastReceiverAction` (merged into the manifest, not hand-written) is `exported="true"` with no `android:permission` on the `FIRE_SETTING` action — inherent to how the Locale/Tasker plugin API works, since Tasker itself holds no special permission when firing, so any app on the device can trigger task creation while this is on. `taskerIntegrationEnabledFlow` (`UserPreferences`) therefore defaults to **off**; `CreateTaskRunner.run` checks it first and returns an error result rather than creating anything when it's disabled.

**Theming:** `ui/theme/` implements M3 Expressive with a warm coral palette by default (see `design/README.md` / `design_handoff_yata/README.md` for the original design tokens/handoff — these HTML/JSX files are non-executable design references, not code to import from). Accent colors for lists/projects/tags/people are named `accentA`..`accentP` (plus a literal `"error"` for tags) resolved through `LocalYataAccents`, not raw `Color` values, so accent pickers (`ColorPicker`, `IconPicker` in `ui/widgets/`) work uniformly across entity types.

`ThemeMode` is `SYSTEM / LIGHT / DARK / AMOLED`. AMOLED is a dark *variant*, not a third state: it resolves dark and additionally flattens surfaces to true black (`YataTheme`'s `toAmoled`), so it still composes with dynamic color and custom seeds. It replaced a clock-based `SCHEDULED` mode (deleted along with `ThemeScheduleUtils` and its time pickers); a persisted `SCHEDULED` value no longer parses and falls back to `SYSTEM`. `WidgetTheme` resolves `ThemeMode` independently for home-screen widgets — AMOLED resolves dark there too but deliberately skips the true-black treatment, since a pure-black panel on the launcher wallpaper reads as a hole. Any new `ThemeMode` value must be handled in both places.

**Settings (`ui/screen/settings/SettingsScreen.kt`):** the root is a searchable hub with destinations defined by `SettingsDestination` (Appearance & Display, Navigation & Features, Sound & Feedback, Task Defaults, Notifications, Privacy & Security, Data Management, Backup & Sync, Help & About). Subsections still use the shared `SettingsSectionHeader` / `SettingsSectionCard` / `SettingsToggleRow` composables in that file — use them rather than re-copying a section's scaffolding. Task defaults that used to be hardcoded now live here and are read via `MainViewModel`: `defaultDueDate` (`DefaultDueDate.TODAY/TOMORROW/NONE`, resolved in `NewTaskSheet`), `defaultPriority`, `trashRetentionDays` (7/30/90/Forever — `0` means keep forever and skips `purgeOldTrash` entirely, and `TrashScreen`'s "days left" label reads the setting instead of asserting 30), `autoArchiveDays`, `undoWindowSeconds`, and the notification toggles. Persisted enum/priority values are validated on read in `UserPreferences` and fall back to the default rather than throwing.

**Localization (`res/values/strings.xml`):** English (`en-US`) is the source language, declared by `tools:locale="en"` on `<resources>` and by `res/resources.properties`' `unqualifiedResLocale`. The bulk extraction is **done** (351 → ~0 over several passes); `strings.xml` now holds ~1350 strings and 38 plurals, and **24 translated locales** exist (`values-bn/cs/de/es/fr/gu/hi/id/it/kn/ml/mr/nl/pa/pl/pt/ro/sv/sw/ta/te/tl/tr/vi`) with genuine translations, not just present keys — so any new string has to be added to all 24 files, which makes the reuse-before-create discipline below load-bearing rather than stylistic. `./gradlew :app:lintLocaleParity` fails the build if a key exists in `values/` but is missing from any locale (currently clean, all 24 at parity); it does not check translation *quality* — a locale can hold 100% English content and still pass, which is exactly how three of the twenty-four had a Spanish/French/Portuguese-labeled `strings.xml` fall roughly 130 keys behind real translations across several feature additions before that got caught and fixed. Run `./gradlew :app:lintHardcodedStrings` for the current count ranked by file — but treat it as a floor, not a total: its pattern only catches Kotlin string literals shaped like `Text("…")`/`text = "…"`/`label = "…"` etc., so it won't catch one passed as a positional constructor argument to an unrelated data class (a Compose-visible bottom-nav/nav-rail tab label was hardcoded in English this way for some time — the string resource existed and was already translated in all 24 locales, it just wasn't being read), and UI polish since the report was last accurate has reintroduced some literals (`NewTaskSheet`'s smart-add preview, `ArchiveScreen`'s section headers and unarchive snackbar, `TrashScreen.deletedLabel`) that the report does not flag. New UI text must go through `stringResource`/`pluralStringResource` (or `context.getString` outside composables), never a literal.

Naming: `action_*` (buttons/menu labels), `cd_*` (contentDescription), `<screen>_*` (screen-specific). Reuse the shared `action_*`/`cd_*` entries instead of adding a per-screen copy of a common word. Anything with a count uses `<plurals>` rather than string concatenation, and interpolated values use positional args (`%1$s`) so translators can reorder them.

Adding a language is only: create `res/values-<code>/strings.xml`, translate the values (never the `name` attributes). `androidResources.generateLocaleConfig = true` regenerates the locale config from whichever folders exist and injects `android:localeConfig` into the merged manifest, so the language appears in Android 13+'s per-app language picker with no list to update by hand. Missing keys fall back to English, and lint's `MissingTranslation` reports them once a second locale exists.

Debug builds enable `isPseudoLocalesEnabled`, adding **en-XA** (accented/padded — anything still rendering plain English is hardcoded, and clipped layouts won't survive a longer language) and **ar-XB** (right-to-left). Both work without any translation existing, which makes them the practical way to test translation readiness now.

**Export/import (`util/`):** `JsonExporter` (full backup/restore), `IcsExporter` (calendar `.ics`), `MarkdownExporter` (plain-text task list for clipboard/share) all operate on the same domain models, independent of the DB layer. `JsonExporter` includes portable `UserPreferences` settings but deliberately excludes/preserves device-local credentials, sync endpoints, last-run state, app-lock material, and install-local photo Uris; check `NON_PORTABLE_KEYS` plus the sync-only preserved names/prefixes before adding a new preference to backups. Malformed portable setting rows are ignored with a warning during backup/sync import so one bad setting does not poison an otherwise valid snapshot. `JsonExporter` carries **photo bytes**, not just paths: profile/person photos are `file://` Uris into the app's `filesDir`, so a path-only backup restored a dangling reference. Person avatars get a `photoData` (base64) field alongside `photoUri`, and the user's own avatar rides at the JSON root since it lives in DataStore, not the DB. Backwards compatible both ways — an old backup with no `photoData` falls back to `photoUri`, and a restore only overwrites the profile photo when the backup actually carries one. Unit tests touching the payload need the `org.json` JVM dependency: the `android.jar` stubs throw, which turns every `JSONObject` assertion into an opaque `RuntimeException`.

**Debug signing:** `:app`'s `debug` signingConfig is overridden in `app/build.gradle.kts` to use `debug.keystore` at the repo root (alias/passwords are the standard `androiddebugkey`/`android`), so a debug build from any dev machine installs over the others without an uninstall. It is deliberately *not* `~/.android/debug.keystore` — that one is the machine-wide default every other Android project signs with, and replacing it there would force an uninstall on all of them instead. Gitignored via `*.keystore`, so a new machine needs the file copied across by hand; when it's absent the config is skipped and the build falls back to the default debug key rather than failing.
